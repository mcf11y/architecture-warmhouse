### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать и выключать отопление в своих домах через обновление статуса датчика (`PATCH /api/v1/sensors/:id/value`).
- Система поддерживает регистрацию датчиков отопления (создание, обновление, удаление) — однако подключение выполняется только специалистом при выезде на объект.
- Управление происходит синхронно: сервер отправляет команду на датчик и ожидает ответа.

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс (`GET /api/v1/sensors`, `GET /api/v1/sensors/:id`).
- Система получает данные о температуре с датчиков через синхронный HTTP-запрос к внешнему сервису `temperature-api`.
- Поддерживается запрос температуры по конкретной локации (`GET /api/v1/sensors/temperature/:location`).
- При запросе списка датчиков данные температурных сенсоров автоматически обогащаются актуальными показаниями из внешнего API в реальном времени.

### 2. Анализ архитектуры монолитного приложения

- **Язык программирования:** Go 1.22.
- **Web-фреймворк:** Gin — HTTP-роутер и middleware.
- **База данных:** PostgreSQL 16 с драйвером pgx v5 и пулом соединений (`pgxpool`). Единственная таблица `sensors` хранит все данные о датчиках.
- **Архитектура:** Классический трёхслойный монолит:
  - `handlers/` — HTTP-обработчики (Presentation layer).
  - `services/` — бизнес-логика и интеграция с внешним API (Business Logic layer).
  - `db/` — прямые SQL-запросы к PostgreSQL (Data Access layer).
  - `models/` — структуры данных (доменная модель).
- **Взаимодействие:** Полностью синхронное. Запросы обрабатываются последовательно. При получении данных с температурных датчиков выполняется синхронный HTTP-запрос к внешнему сервису `temperature-api` (таймаут 10 сек).
- **Масштабируемость:** Ограничена вертикальным масштабированием. Горизонтальное масштабирование затруднено из-за единой БД и монолитной структуры.
- **Развертывание:** Docker-контейнер (multi-stage build на Alpine Linux). Обновление любого компонента требует пересборки и перезапуска всего приложения.
- **API:** REST API с версионированием (`/api/v1`), поддерживает CRUD-операции над датчиками.
- **Типы устройств:** Поддерживается единственный тип — `temperature`. Расширение на другие типы устройств не предусмотрено в текущей архитектуре.

### 3. Определение доменов и границы контекстов

**Текущее состояние (As-Is):** Единый bounded context — «Управление датчиками температуры». Вся логика (работа с датчиками, получение телеметрии, хранение данных) сосредоточена в одном монолитном приложении.

**Целевое состояние (To-Be):** Для реализации экосистемы умных посёлков выделены следующие домены и bounded contexts:

| Домен | Bounded Context | Ответственность |
|-------|----------------|-----------------|
| Управление пользователями | User Management | Регистрация, аутентификация, авторизация, профили пользователей, управление домами |
| Управление устройствами | Device Management | Регистрация устройств, конфигурация, поддержка различных типов (отопление, освещение, ворота, камеры), подключение устройств партнёров по стандартным протоколам |
| Телеметрия | Telemetry | Сбор, хранение и предоставление данных телеметрии с устройств (температура, состояние, показания) |
| Сценарии автоматизации | Scenario Management | Создание и выполнение пользовательских сценариев («если температура < 18°C — включить отопление») |
| Уведомления | Notifications | Отправка уведомлений пользователям о событиях в системе (тревоги, срабатывание сценариев) |

Домен «Управление устройствами» проектируется с расширяемой моделью типов устройств, что позволяет подключать новые, ещё не определённые типы датчиков и исполнительных механизмов без модификации ядра системы.

### **4. Проблемы монолитного решения**

- **Единая точка отказа.** Падение любого компонента (обработчик запросов, подключение к БД, HTTP-клиент) приводит к полной недоступности всей системы.
- **Сильная связанность (Tight Coupling).** Обработчики напрямую зависят от конкретных реализаций `db.DB` и `services.TemperatureService` — нет интерфейсов и инверсии зависимостей. Это затрудняет тестирование и замену компонентов.
- **Нет самообслуживания.** Пользователь не может самостоятельно подключить датчик — требуется выезд специалиста.
- **Синхронное взаимодействие.** Каждый запрос на получение датчиков последовательно выполняет HTTP-вызовы к `temperature-api` (таймаут 10 сек на каждый). При N температурных датчиков в `GetSensors` выполняется N последовательных запросов — время ответа растёт линейно.
- **Невозможность независимого масштабирования.** Нельзя масштабировать сбор телеметрии отдельно от управления устройствами — всё в одном процессе.
- **Единственный тип устройства.** Поддерживается только `temperature`. Добавление освещения, ворот, камер потребует модификации ядра монолита (моделей, обработчиков, БД).
- **Отсутствие аутентификации и авторизации.** API полностью открыт, нет понятия пользователей и прав доступа. Невозможна работа в модели SaaS.
- **Единая БД с одной таблицей.** Схема не готова к мультитенантности, региональному масштабированию и хранению разнородных данных (телеметрия, сценарии, пользователи).
- **Неделимое развертывание.** Обновление любой части функциональности требует пересборки и перезапуска всего приложения, что приводит к простою.

# Задание 2. Проектирование микросервисной архитектуры

# Задание 4. Создание и документирование API

### 1. Тип API

Для взаимодействия микросервисов используются два типа API:

**REST API (OpenAPI 3.0)** — для синхронного взаимодействия:
- Запросы от API Gateway к микросервисам (управление устройствами, запрос телеметрии, CRUD-операции).
- Межсервисные вызовы (Scenario Service -> Device Service для отправки команд при срабатывании сценария).
- Формат данных: JSON. Версионирование: `/api/v1`. Стандартные HTTP-коды ответов.
- Обоснование: REST — простой, широко поддерживаемый стандарт, подходящий для CRUD-операций и запросов с немедленным ответом.

**AsyncAPI 2.6** — для асинхронного взаимодействия через Kafka:
- События телеметрии (`telemetry.received`), регистрации устройств (`device.registered`), тревоги (`device.alert`), срабатывания сценариев (`scenario.triggered`).
- Обоснование: телеметрия генерирует высокий поток данных, сценарии и уведомления не требуют немедленного ответа — асинхронная модель обеспечивает слабую связанность и устойчивость к пиковым нагрузкам.

### 2. Документация API

**REST API (OpenAPI 3.0):**

- [Device Service API](schemas/api/device-service.yaml) — 5 эндпоинтов: список типов устройств, получение устройства, регистрация, обновление статуса, отправка команды.
- [Telemetry Service API](schemas/api/telemetry-service.yaml) — получение телеметрии устройства с фильтрацией по времени.

**Асинхронное API (AsyncAPI 2.6):**

- [Async API — события Kafka](schemas/api/async-api.yaml) — каналы: `telemetry.received`, `device.registered`, `device.alert`, `scenario.triggered`.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

- Get All Sensors
